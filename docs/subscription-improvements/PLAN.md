# План доработок Xkeen-UI

Дата: 25 октября 2026. Статус: планирование до реализации.
Репозиторий: https://github.com/umarcheh001/Xkeen-UI
База: main, commit afefd60ca85b4d04f3a41c90d05de38a2f635455.

## Первичный анализ

Есть отдельные сервисы Xray и Mihomo. subscription_schedule.py выравнивает интервальные сроки, но не реализует cron. В Xray уже есть Python re для фильтров; нужно отличить их от поиска по карточкам. Оба сервиса уже условно перезапускают ядро при пакетном обновлении: требуется воспроизведение лишнего рестарта. Есть pytest, Playwright и сборка Vite. У подключённого GitHub-аккаунта нет push-доступа к upstream; перед публикацией проверить fork.

## Порядок работы

1. Уточнить ядро, установленную версию, устройство, область regex и расписания; записать ответы в DECISIONS.md.
2. Подготовить ветку, проверить инструкции проекта, CI и путь публикации через fork.
3. Воспроизвести проблемы на базовом commit; снять исходные скриншоты и показатели на обезличенных данных.
4. E1: cron, API, интерфейс и совместимость настроек.
5. E2: общая загрузка одинаковых источников и определение необходимости рестарта.
6. E3: подсказки и регулярные выражения.
7. E4: ускорение загрузки подписок по результатам профилирования.
8. E5: закрепление шапки и целевые улучшения для слабых устройств.
9. Адресные регрессионные проверки, сборка, необходимые проверки CI и скриншоты после.
10. E6: документация и PR в main исходного репозитория со ссылкой в чате.

## Проверки и измерения

Backend: старые интервалы, cron, отключение, ошибки, пропущенные и конкурентные запуски, число скачиваний и рестартов. UI: сохранение расписания, ошибки cron/regex, длинные названия, клавиатура, узкий экран, масштабирование и прокрутка.

Замерять одинаковые наборы 1/10/50 подписок и 100/1000/5000 подключений: время до отображения, число запросов, объём ответа, фильтрация, фоновые опросы. Это сценарии измерения, не обещанные пределы поддержки. Фиксировать окружение и медиану нескольких запусков. Бюджет ускорения определить после исходного замера, до оптимизации.

Испытания на Keenetic/Entware учитывать отдельно от локальных. CPU throttling браузера не считать проверкой на реальном роутере. Не переписывать весь сайт: оптимизировать измеренные узкие места.

## Доказательства в PR

Скриншоты до/после: форма расписания, длинное название, regex с результатами, шапка при прокрутке. Одинаковые тема, viewport и данные. Изображения должны быть доступны рецензенту из описания PR. Для невизуальных изменений приложить измерения и счётчики. Не публиковать реальные URL подписок, токены и конфигурационные секреты.

План и решения включить в рабочую ветку. Эпики пока ведутся в Markdown без GitHub Issues. Код приложения на этапе планирования не изменён; PR пока не создан.

## Уточнение области после ответов

Реализация E1–E4 относится только к Xray; Mihomo не изменять. E3 относится к сохраняемому «Фильтру по имени»: сценарий исключения узлов с ws. Целевая установка: 3.0.2, Keenetic Ultra, Keenetic OS 5.1.8. До изменения кода сравнить установленную версию с текущей main. Использовать отдельный cron каждой подписки с сохранением интервалов и часовым поясом роутера.

## Условие публикации, добавленное менеджером

Перед созданием PR предоставить описание со всеми предназначенными для него скриншотами и дождаться явного согласования. Реализацию и локальные проверки можно завершить до этого шага. Роутер использовался только для чтения; изменения на него не установлены.
